## What Changelog is

A capture tool with four verbs: **log** a note, **plan** a date, **get
reminded**, and **check** what happened. It is not a reader of your notes.
The web app is where you read, search, look back and change settings.

Jamie, 2026-10-29, on the fourth: "showing recent activity would be a good
thing in there too, because it's a way to confirm what did the app do and
what did other entities do. That would also potentially allow us to hook in
notifications on the activity feed."

- **Open to typing.** The keyboard is up when the app opens. Typing and
  sending a line takes two taps.
- **Never lose a note.** Everything goes through an offline queue and is
  sent when the phone can, without making duplicates.
- **Tags are one tap.** Pinned tags, recent tags, and a sticky tag that stays
  on for a trip.
- **The software metaphor,** in small doses: today's version in monospace at
  the top, "Filed in 5.4.278", an empty state of "No changes yet in 5.4.278".
- **Never reads your words.** Changelog asks for `notes:write`,
  `media:write`, `upcoming` and `activity`, never `notes:read`. The activity
  it reads says what happened, through what, and on which day, never what a
  note said (see Activity, below). A lost phone or a leaked token can add to
  your notes and see that things happened, but can't read them.

- The header is today's version and the streak, or "Nothing yet in 5.4.278".
- The tag row has pinned tags first, then recent ones. A long press makes a
  tag sticky until you turn it off.
- Attach a photo, take a picture, or record a voice memo. "Here" adds the
  phone's spot and can offer a nearby business, as the web's Here does.
- Below is today's activity, from every channel: "Filed in 5.4.278 via
  Changelog", "Reply filed", "Added by Claude". What this phone has queued
  shows as waiting. Swipe to edit or delete a note Changelog wrote.
- A badge earned by the note shows as a short toast, only while "Show
  badges" is on.
- The button's word is Jamie's to pick: "Commit", "Ship", or a plain "Add".

**2. Upcoming**

- The list of dates, each with the server's own line ("Mom turns 7.0.0. A
  major release.", "Maine. June 14 - 21.").
- Add or edit: kind (birthday, anniversary, trip, event), title, the date,
  the year if known, an end date for a trip, a destination typed as text,
  a tag, and the reminder days (7, 1 and 0 by default; 14, 1 and 0 for a
  trip).
- Delete.

**3. Activity**

- The activity log, newest first, from every channel, each row saying when,
  through what (email, the web, Changelog, Terminal, Claude), what happened
  and on which day. Tap a note row to open that day on the web.
- A "since you last looked" line. The phone keeps that marker itself, so the
  server stores nothing new.
- Filter by kind: notes, email, badges, Upcoming, connections, problems.

**4. Settings**

- Which connection this is ("Changelog on Jamie's iPhone"), and Sign out,
  which revokes the token.
- Notifications: Upcoming reminders, activity, and the daily prompt.
- Pinned tags, and whether Here is on by default.
- Links out: Open Release Notes, the guide, and `/delete/`.

**5. Everywhere else**

- **Share extension:** a short Log sheet holding whatever was shared (a link,
  a photo, some text), with the tag row.
- **Widgets:** small (version and streak); medium (version, a Log button,
  the next Upcoming line); Lock Screen (the version, inline).
- **App Intents:** "Add to Changelog" in Siri and Shortcuts, the Action
  Button, and a Control Center control.
- **Apple Watch** dictation, later.

## Notifications, with no push server

Every notification is local: scheduled by the app on the phone, from data
it fetched. Release Notes keeps no device tokens and no Apple push key (a
secret it would otherwise have to hold), and notifications still fire when
the phone is offline.

- **Upcoming reminders.** On each reminder day, at the account's send time,
  with the same line the email carries that morning. The server works out
  which reminders fall on which days, so the leap-day rule and the reminder
  days live in one place, and the Android app can't get them wrong either.
- **The daily prompt** (optional, call 3). "You're 5.4.278 today. What
  changed?" at send time, which opens Log.
- **A rolling window.** iOS keeps at most 64 pending notifications an app,
  so the app schedules about 14 days ahead and tops up whenever it opens and
  in background refresh.
- **Activity notifications** (off until turned on in the app). Each kind
  is chosen in the app's settings:
  - notes added by someone else: an agent, another token, an import, or an
    email reply when you're away from the phone;
  - problems: an email that wasn't filed, the account stopped, a connection
    ended;
  - badges earned.
  Never your own notes from this phone, and never the daily email going out.
  They come from background refresh, so iOS decides when. That might be
  minutes or hours, not instant. Instant would need real push (see below).
- **Real push, later.** Apple push needs the paid Developer Program, an APNs
  key (a secret Jamie would keep), device tokens stored per account, and a
  worker on the table's stream sending them. That is its own design, like
  webhooks. Nothing in v1 blocks it: activity rows are already in the table,
  and the stream already exists.
- **The rule this changes.** AGENTS.md says Upcoming reminders "travel only
  in the daily email", and the calendar link carries "no alarms". Phone
  notifications would be a second channel: chosen on that phone, carrying
  the email's own lines, and with no extra email. AGENTS.md would record it
  with Jamie's words (call 2).

## Checking the API against the app

Each thing the app does, the call it needs, and what that changes in the plan.

| The app | Call | Against the plan |
|---|---|---|
| Version, streak, "nothing yet" | `GET /v1/me` | **Changed:** add `wrote_today`, `streak`, `send_time`, `tz`, `paused_until` and `status` |
| Widgets and notifications that fire offline | `GET /v1/me` `days` | **New:** the next 14 days, each with its version. Clients never port the version arithmetic, and the birthday is never sent |
| A text note | `POST /v1/notes` | **Changed:** takes `written_at`, the moment it was typed. A note queued at 11:58pm and sent at 12:05am files to the day it was written (the account's local day), unless `date` says otherwise |
| Safe retries | `Idempotency-Key` | **Changed:** receipts last 24 hours today, which a phone offline over a weekend can outlast. Keep them 7 days on `/v1` |
| The tag row | `GET /v1/tags` | **Changed:** the pinned list first, then the tags used most in the last 30 days, with counts and last use |
| Pinned tags | `PUT /v1/tags/pinned` | **New,** if pins live on the account (call 4) |
| Sticky tag | none | the app keeps it |
| Photos, camera, voice | `POST /v1/uploads`, then the note names its uploads | **Changed:** see "Files", below. The one infra change |
| Here | `POST /v1/places/here` `{lat, lon, accuracy_m}` | **New to v1,** as the web's: the spot, its neighbourhood and up to six nearby businesses |
| A city typed by hand | `GET /v1/places?q=` | **New to v1,** the web's city search |
| Edit or delete a note sent today | `PUT` and `DELETE` on its own notes, with `revision` | as planned |

### Files

This is where the app pushes the API hardest.

- MCP takes files as base64 in the call: at most 4 files and 4 MB together,
  because a synchronous Lambda invoke carries 6 MB. A phone photo or a
  five-minute voice memo can be that size alone.
- The web uses signed upload forms instead: 50 MB a file, 20 files a note,
  200 uploads and 2 GB a day per account. `/v1` should use those too.
- **Infra change, flagged.** The signed forms and the attach step that
  follows them run in the web server today, under a session. The token
  server's roles were built without upload rights. Phase 3 needs the token
  server, or its capture function, to sign forms for the pending prefix and
  run the same attach, with the same checks. That is a role change in the
  stack.
- A form lives five minutes, but a background upload on a weak signal can
  start later than that. Either the app asks for the form just before it
  uploads, or `/v1` forms last longer (30 minutes). *Recommend the app asks
  late,* with no change to the server.
- **HEIC never reaches the email.** iPhone photos are HEIC, and a HEIC gets
  no thumbnail (AGENTS.md, Thumbnails), so it never appears in the morning
  email. A native app sends whatever it's given. I haven't checked whether
  the web's picker gets JPEG or HEIC from an iPhone. Its accept list names
  HEIC, so web uploads may be HEIC too. Either Changelog asks the photo
  picker for its "compatible" JPEG (place and time kept), or the server
  learns to make HEIC thumbnails (call 1).

## Android, for [a cousin]

Nothing above is iPhone-only on the API side. Each piece has an Android
match: WorkManager for the queue, local notifications on a schedule, Glance
widgets, a share target and a Quick Settings tile. The `days` and
`reminders` answers mean [the Android app's builder] never writes the version arithmetic or the
reminder rules in Kotlin. The only platform-specific server work is the OAuth
callback, which the API plan already covers.
